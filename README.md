# book_marketplace_analysis
# Книжный маркетплейс: системный анализ
Полный цикл системного анализа книжного маркетплейса с интеграциями МойСклад (учёт товаров, резервы для заказов,
отгрузки),  Яндекс Доставка (доставка курьером до двери), ЮKassa (проведение платежа) и Unisender Go (отправка транзакционных писем)

## О проекте

Маркетплейс книг с четырьмя внешними интеграциями.  Реализует возможность регистрации, добавления товаров (для продавцов) и
выбора книг из общего каталога (для покупателей), оформления заказа с онлайн-оплатой и получением транзакционных уведомлений на всех этапах доставки. Асинхронные взаимодействия внутри платформы (доменные события, повторные попытки синхронизации, транзакционные письма) происходят с помощью брокера сообщений RabbitMQ

**Артефакты анализа:**
- Use case диаграмма
- BPMN диаграмма основного процесса (жизненный цикл заказа от создания до доставки)
- C4-модель (уровень контекста, контейнеров и компонентов)
- 5 sequence-диаграмм по ключевым сценариям
- ER-диаграмма базы данных
- Описание 26 эндпоинтов API 
- Реестр из 11 интеграционных сценариев с 4 внешними системами
- Спецификация интеграций, контракты запросов, маппинги полей, обработка ошибок по классам

**Бизнес-контекст и роли:**

Четыре роли в системе, каждая со своими use case и набором API:
- **Покупатель** — поиск книг, корзина, оформление и оплата заказа, история заказов
- **Продавец** — добавление и редактирование своих товаров, статистика продаж
- **Сотрудник склада** — список заказов на сборку, отметки этапов (собран, готов, передан курьеру), создание отгрузки в МойСклад
- **Администратор** — управление пользователями, модерация товаров, просмотр заказов и данных интеграций через встроенную админ-панель Django

Роли отражены в архитектуре: отдельные контроллеры (Catalog API для продавца, Warehouse API для склада сотрудника склада, User/Orders API для покупателя разграничение доступа через JWT с ролями, разная видимость данных.

## Архитектурные решения 

**Распределённые транзакции и согласованность**
- Оформление заказа построено по паттерну Saga с компенсацией: резерв товара (МойСклад) -> платёж (ЮKassa) -> подтверждение резерва; при ошибке оплат компенсация отменой резерва.
- Физическая передача курьеру может произойти без учёта в ERP (МойСклад). При недоступности МойСклад отгрузка доводится асинхронно

**Идемпотентность**
- Реализована в четырех контурах: резерв в МойСклад, платёж и вебхук со статусом оплаты в ЮKassa, транзакционные письма
  (отправка в Unisender Go и запись в журнал)

**Отказы и повторные попытки**
- Классификация отказов: 4xx - бизнес-отказ без retry со статусом и понятным сообщением клиенту;
- 5xx - временный сбой. Происходит retry с экспоненциальной задержкой и лимитом 5 попыток и уведомлением
  владельца при исчерпании
- Стратегия ACK/NACK в брокере: клиентские ошибки подтверждаются без повтора, серверные возвращаются в очередь
- Недоступность МойСклад не останавливает бизнес. Товар сохраняется как pending (202 Accepted), отгрузка как
  shipment_pending, доведение происходит асинхронно

**Асинхронность и интеграции**
- События через RabbitMQ. Уведомления и retry вынесены из синхронного контура
- Паттерн интеграции выбран по возможностям системы: ЮKassa — push (вебхук), Яндекс Доставка — pull (Scheduled Worker запрашивает статусы
  по расписанию и публикует события изменений)
- Stateless веб-сервер и отдельные воркеры (Sync, Scheduled, Notification). Фоновая нагрузка не влияет на время ответа, воркеры масштабируются
  независимо

**Безопасность**
- Проверка подписи вебхука оплаты
- Хеширование паролей PBKDF2-SHA256;
- Ролевая модель с 401/403 на уровне API при отсутствии аутентификации/прав
- Жизненный цикл персональных данных по 152-ФЗ "О персональных данных": согласие при регистрации, удаление аккаунта и данных по требованию пользователя
